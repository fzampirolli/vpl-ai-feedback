# VPL AI Feedback

A system that generates **qualitative, Socratic-style feedback** (via LLM), complementary to the objective, test-case-based grading performed by **VPL (Virtual Programming Lab)** on Moodle. For each student, the submitted code is sent to an AI provider together with a rubric defined by the instructor; the AI identifies the drawn question type, applies the corresponding rubric, and produces a detailed evaluation — without ever replacing VPL's objective grade or the instructor's judgement.

The project supports both **single-question** VPL activities (e.g., formative exercises, quizzes) and activities with **multiple parameterized questions per student** (e.g., exams with 3 questions randomly drawn from types A/B/C).

When a VPL activity has **only one code submission**, the question can be **static** (the same statement for every student) — in that case there is no random draw of variants, and the MCTest tool is not needed; the official statement extracted from VPL simply does not vary from student to student. When the activity involves **parameterized** questions instead (a distinct variant per student, as in exams), the questions are generated by the MCTest tool and delivered to students both as a printed PDF handout and as a file attached to the VPL activity itself — it is from that attachment/statement, extracted from VPL's `execution.txt`, that `core/utils.py` obtains the **official statement** used as primary evidence for the AI to correctly identify each question's drawn type.

> Reference: Zampirolli et al. (2026), *"Intelligent Feedback for Individualized Introductory Programming Exercises"* (see [References](#references)).

## How it works

1. Student submissions are exported from Moodle/VPL as one folder per student (`<Name> - <login>/<timestamp>/` with the code, and `<timestamp>.ceg/execution.txt` with the actual test-case execution results).
2. `main.py` walks through each student folder, builds a prompt per question (student code + official statement of the drawn question + real VPL execution evidence + the student's other codes as style context) and sends it to the configured LLM provider.
3. The AI responds with the identified question type, its confidence in that identification, and the evaluation according to the corresponding rubric, including a structured grade (`NOTA FINAL: X/Y`).
4. Results are saved per student (`rubrica.txt`, with caching — re-runs don't pay for the API again) and consolidated into a CSV comparing the Moodle grade vs. the AI grade, per question.
5. `enviar_email.py` emails each student their individual report, flagging when any question had low confidence in type identification (recommending manual review by the instructor).

The AI grade never replaces the VPL grade: it is informative/formative, and the rubric/prompt used are always defined and approved by the instructor (even if drafted with AI assistance).

## Project structure

```
main.py                  Orchestrates batch grading (async, with limited concurrency)
core/
  grader.py              Builds per-question prompts, calls the LLM, generates rubrica.txt/CSV/ALL.txt
  utils.py               Extracts AI grades, reads submissions and VPL's execution.txt
providers/
  __init__.py            Factory: picks the LLM client based on config.yaml (llm.provider)
  base.py                Shared logic: model fallback, retries, backoff on 429 errors
  groq.py                Client for the Groq API (OpenAI-compatible)
  deepseek.py            Client for the DeepSeek API (OpenAI-compatible)
  gemini.py              Client for the Google Gemini API
enviar_email.py           Emails each student's rubrica.txt via SMTP (with a TLS fallback)
atualizar_conceitos.py    Updates letter grades (A–F) in an .xls spreadsheet from Moodle's grade CSV
busca.sh                  Lists submissions that don't have a rubrica.txt yet
renomear_pastas.sh        Renames Moodle-exported folders to the "Name - login" pattern
run.sh                    Wrapper around main.py with optional logging and timing stats
config.yaml.example       Configuration template (copy to config.yaml, never commit it)
promptP1.txt / promptP2.txt / promptP3.txt
                           Prompts for SINGLE-question activities per student (quizzes)
promptProva1.txt / promptProva2.txt
                           Prompts for MULTIPLE-question exams per student (types A/B/C)
p1moodle0/                 Sample exported data (kept in the repo as a reference)
old/                       Previous versions of the scripts (kept for history)
```

## Installation

```bash
git clone https://github.com/fzampirolli/vpl-ai-feedback.git
cd vpl-ai-feedback
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

`atualizar_conceitos.py` has its own dependencies (`xlrd==1.2.0`, `xlwt`, `xlutils`, `pandas`), which it installs on demand the first time it runs.

## Configuration

```bash
cp config.yaml.example config.yaml
```

Edit `config.yaml` (never committed — already in `.gitignore`) with:

- **`llm.provider`**: `groq`, `deepseek`, or `gemini`.
- **`<provider>.api_key`** and **`<provider>.models`**: API key and list of models (the first is tried first; on failure, the next is tried — useful to work around rate limits/outages).
- **`grading.prompt_file`**: which prompt/rubric file to use (e.g., `promptP3.txt` for a single question, `promptProva2.txt` for a 3-question exam).
- **`grading.weights`**: weight of each question, e.g., `q1: 50` for a single-question activity, or `q1: 33` / `q2: 33` / `q3: 34` for a 3-question exam.
- **`paths.student_base_dir`**: folder containing the exported Moodle submissions.
- **`email.*`** and **`templates.*`**: SMTP server and the text of the email sent to each student.

## Usage

**Run AI grading** (generates `rubrica.txt` per student + CSV + consolidated file):

```bash
bash run.sh config.yaml --log     # --log writes output to log_correcao_<date>.txt
# or directly:
python3 main.py --config config.yaml --concurrent 3
```

Outputs generated alongside the student folder:
- `<student_base_dir>/<student>/<submission>/rubrica.txt` — individual report (also acts as a cache: if it already exists, the API is not queried again).
- `<student_base_dir>_relatorio.csv` — Moodle vs. AI comparison, per question, with columns for identified type, confidence, and a `Revisar_Manualmente` (needs manual review) column.
- `<student_base_dir>_ALL.txt` — all individual reports concatenated.

**Check for pending submissions** (no `rubrica.txt` yet):

```bash
./busca.sh p1moodle
```

**Email the reports to students:**

```bash
python3 enviar_email.py
```

**Rename Moodle-exported folders** to the `Name - login` pattern expected by the rest of the pipeline:

```bash
./renomear_pastas.sh /path/to/exported_folder
```

**Update letter grades (A–F) in a grade spreadsheet** from Moodle's submission CSV:

```bash
python3 atualizar_conceitos.py notas_turma.xls Prova1_submissions.csv -o notas_atualizado.xls
```

## Single-question vs. multi-question activities

The same pipeline (`main.py` → `core/grader.py`) handles both formats; what changes is the prompt file and the `weights` dictionary:

- **Single question** (`promptP1.txt`, `promptP2.txt`, `promptP3.txt`): `grading.weights` has a single key (e.g., `q1: 50`). The prompt describes the possible types for that question and each one's rubric.
- **Multi-question / exam** (`promptProva1.txt`, `promptProva2.txt`): `grading.weights` has one key per drawn question (e.g., `q1`, `q2`, `q3`). Each question is graded independently by the AI (one API call per question, all for the same student), but the final `rubrica.txt` and the CSV consolidate all three grades and the student's total.

In both cases, the prompt requires the AI to explicitly state the **identified type** and its **confidence** in that identification before applying the rubric — later used to automatically flag, in the CSV, which students deserve manual review by the instructor.

## LLM providers

`providers/__init__.py` implements a simple factory: `get_client(config)` reads `llm.provider` and instantiates the corresponding client. All of them inherit from `providers/base.py`, which handles:

- fallback across multiple configured models;
- up to 3 retries per model, with exponential backoff (honoring `retry-after` on 429 errors);
- immediate abort on authentication/balance errors (401/402).

To add a new provider, create a subclass of `BaseLLMClient` implementing `_raw_call()` and register it in the `mapping` dict in `providers/__init__.py`.

## Security

- `config.yaml` (containing API keys and SMTP password) is in `.gitignore` — it must never be committed. Use `config.yaml.example` as a template.
- Student data (submission folders, grade CSVs, reports) is also ignored by default, except for the `p1moodle0/` example.
